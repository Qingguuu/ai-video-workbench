# 项目编码工作流（五阶段规格驱动）

> 本文件是本项目的强制性协作流程，用于防止对话式开发跑偏。所有编码任务默认遵循本工作流，除非用户明确说「跳过流程」。

## 总原则

1. **先文档后代码**：规格未确认前不写实现代码。
2. **关口确认**：每个阶段结束必须停下，等用户明确批准（如「通过」「可以」「继续」）才能进入下一阶段；用户只是提意见不算批准。
3. **产出物落盘**：每阶段产出写入 `docs/workflow/<任务名>/`，作为跨会话的持久上下文。
4. **新会话先恢复上下文**：处理编码任务前，先读取该任务目录下的最新产出物，确认当前所处阶段，再继续。
5. **变更走路由**：用户中途提意见时，按下方「变更处理」规则分类处理，不得直接动手改代码。

## 任务分级

| 级别 | 判定标准 | 流程 |
|---|---|---|
| 快速通道 | 改动 ≤ 2 个文件、无新依赖、无架构决策、需求无歧义 | 口头计划 → 用户确认 → 实现 → 自查验证 |
| 标准任务 | 不满足以上任一条 | 完整五阶段 |

判定拿不准时，向用户说明情况并让用户选择。

## 五阶段定义

### 1. 需求澄清（Clarify）
- 做什么：复述需求，列出理解要点、假设和歧义，用少量选择题澄清（一次不超过 4 个问题）。
- 产出：`01-requirements.md`（背景 / 目标 / 范围内 / 范围外 / 验收标准）
- 关口：用户确认需求文档

### 2. 规格（Spec）
- 做什么：把需求转成可验收的功能规格，只定义「做什么」，不涉及技术实现。
- 产出：`02-spec.md`（功能点列表 / 每点的验收标准 / 边界与异常场景）
- 关口：用户确认规格

### 3. 计划（Plan）
- 做什么：技术方案 + 任务拆解：涉及哪些文件、每步做什么、顺序、风险点。
- 产出：`03-plan.md`（技术选型 / 文件级改动清单 / 任务顺序 / 风险）
- 关口：用户批准计划

### 4. 实现（Implement）
- 做什么：严格按计划逐任务编码；发现计划有误时停下说明，不得静默偏离。
- 产出：代码 + `04-changelog.md`（实际改动记录，偏离计划处单独标注原因）
- 关口：实现完成，向用户汇报改动摘要

### 5. 验证（Verify）
- 做什么：对照 `02-spec.md` 的验收标准逐条自查或测试，给出通过 / 未通过结论。
- 产出：`05-verification.md`（验收标准逐条核对结果 / 发现的问题及处理方式）
- 关口：用户验收，任务关闭

## 变更处理（防止跑偏的核心规则）

用户在任意阶段提出意见时，先分类再行动：

| 意见类型 | 处理方式 |
|---|---|
| 当前阶段内的小修正 | 立即采纳，更新当前产出物 |
| 改变需求或范围 | 停止当前阶段 → 更新 `01/02` 文档 → 重新过关口，再继续后续阶段 |
| 与已确认规格冲突 | 指出冲突点，让用户二选一：修改规格（回到阶段 2）或维持原设计 |
| 实现期间的新想法 | 记入 `04-changelog.md` 的「待办池」，当前任务完成后统一评估，不打断当前任务 |

## 产出物格式约定

- 目录：`docs/workflow/<任务名>/`（任务名用短横线小写英文）
- 每个文档开头加状态行：`> 状态：草稿 | 待确认 | 已确认`
- 文档保持简短：需求 / 规格 / 验证各不超过 1 屏，计划不超过 2 屏
